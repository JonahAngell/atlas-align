Request type: Refactor; Audit logic or business-rule change

## 2. Implementation Contract
Goal: Create the ATLAS adapter and evaluator registry, normalize the active audit for the portable engine, and migrate existing audit/Logic Builder validations into one canonical transient issue result. Do not add the floating UI, navigation, or inline fixes in this phase.

- PROJECT_TREE.txt
Required generated artifacts: None.
Behavior that must remain unchanged:
- Existing validationPanel output remains available through compatibility rendering.
- Audit documents, assignments, sources, logic, display fields, persistence, preview/export, publication, virtualization, selected-editor DOM, joins, and database behavior remain unchanged.
Definition of done:
- One canonical ATLAS issue result covers verified audit setup and logic checks.
- Existing validation callers delegate to it or remain documented temporary wrappers without duplicate calculations.
- Evaluation invalidation is integrated without broad rendering or persistence.
- Modified files are delivered in a ZIP.
Blocking assumptions or decisions:
- Do not enable field-relationship incompatibility unless authoritative metadata explicitly supports it.
- Do not report missing action when the step type permits no direct action or an active meaningful descendant implements the action.
Implementation flexibility: Preserve proven validation helpers as named evaluators where moving them would increase regression risk.

## 5. Desired Behavior
Required behavior:
- Build normalized ATLAS context from the active audit without mutating it.
- Register named evaluators for audit identity, assignments, source presence/identity, step existence, hierarchy integrity, conditions, actions, joins, math, string transforms, created fields, and Display Fields validity where current evidence supports each rule.
- Preserve existing workbook warnings.
- Canonical rules must include user-requested warnings: missing analyst, backup, developer, name, purpose/description, sources, applicable action, and join type.
- Canonical rules must include user-requested critical issues: missing condition field, missing operator/comparison, missing comparison field/source in field mode, and proven invalid field relationship.
- Additional verified critical candidates: stale source/field references, missing join sides/keys, unsupported join type, malformed conditions, missing parent, hierarchy cycle, created-field forward/removed references, invalid math/string-transform configurations.
- Additional verified warning candidates: no logic steps, duplicate values, created column without name, duplicate created name, unused source, no displayed outputs, duplicate/invalid display preference.
- Rules dependent on unavailable authoritative metadata remain disabled and explain why.
- Parent-action evaluation must inspect step type, enabled descendants, branch applicability, and meaningful completed action.
- Compatibility validateAudit() returns the canonical issue collection in the legacy level/message shape where callers still require it.
- Existing specialized helpers may remain, but duplicate wrapper chains must be removed only after active calls are accounted for.
- Invalidate issue results after relevant audit changes using existing targeted scheduling; do not persist results.
Expected user flow: Existing Readiness validation continues to render while its data source becomes canonical.
Source of truth: Active audit, canonical source identity/catalog helpers, step definitions, hierarchy, and current action/join/condition helpers.
Null/invalid behavior: Malformed structured data becomes an issue rather than throwing the evaluation; duplicate issue instances collapse by stable key.
Error behavior: Evaluator failure is isolated and surfaced safely without exposing audit data.
Preferred implementation: js/23 provides context adapters, evaluator registry, cache/invalidation, and legacy compatibility methods.
Required implementation: One canonical issue result; no UI, navigation, fix, publication, database, or API changes in this phase.

## 6. Acceptance Criteria

2. User-requested severities are represented exactly, except rules explicitly disabled for missing authoritative evidence.
3. Parent action delegates successfully only to a valid active meaningful descendant.
4. Field-relationship issues never rely solely on different names or cross-source status.

6. Duplicate calculations and later wrapper chains are removed only after all active callers are migrated.
7. Issue evaluation is transient, cached/invalidation-aware, and does not cause broad selected-editor rerendering.
8. Imported legacy audit data evaluates without being rewritten.
9. Existing persistence, publication, preview/export, hierarchy, virtualization, and Join Picker behavior is unchanged.
10. Tests cover representative valid and invalid audit contexts, parent-descendant exception, malformed data, and deduplication.
11. No executable reference to js/15-visual-ui-upgrades.js exists.
