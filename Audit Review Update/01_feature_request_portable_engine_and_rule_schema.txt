## 5. Desired Behavior
Required behavior:
- The engine accepts normalized context, rule definitions, and registries supplied by a caller.
- It must not read state.audit or ATLAS globals.
- Validate rule IDs, enabled state, severity, category, priority, evaluator name, optional jump/fix names, messages, and configuration.
- Allowed severities are ok, warning, and critical; applications normally receive warning/critical issue records while ok is aggregate state.
- An unknown evaluator, invalid severity, malformed rule, or evaluator exception must fail safely without executing arbitrary code or suppressing unrelated rules.
- Normalize output fields: ruleId, instanceId, stableKey, severity, category, title, summary, detail, target descriptor, canJump, canFix, and action descriptors.
- Deduplicate by stable key and sort deterministically by severity, priority, category, title, and target.
- Aggregate critical over warning over ok and expose counts.
- Do not mutate input context, rules, or evaluator output.
- Support multiple independent engine instances.
Expected user flow: Not applicable to UI. A caller creates an engine, supplies a catalog and registries, evaluates context, and receives one immutable result.
Data rules:
- JSON contains no executable code.
- Named registries resolve evaluator/action names.
- Disabled rules emit no issues.
- Evaluator failures produce safe diagnostics or a normalized system issue according to documented engine policy.
Source of truth: Caller-provided context and validated catalog.
Missing behavior: Missing optional metadata uses documented defaults; missing required metadata rejects that rule.
Error behavior: One bad rule/evaluator does not prevent unrelated valid rules from evaluating.
Preferred implementation: An IIFE exposing an immutable factory API suitable for classic scripts, such as createAuditIssueEngine(options).
Required implementation: No direct ATLAS dependencies and no eval/new Function/dynamic script execution.

## 6. Acceptance Criteria
1. Two independent engine instances can evaluate different contexts without shared mutable state.
2. Catalog validation rejects malformed rules, duplicate IDs, unsupported severities, and unknown registered names safely.
3. Evaluation normalizes, deduplicates, and deterministically sorts issues.
4. Aggregation returns ok, warning, or critical with exact severity counts and critical precedence.
5. Evaluator exceptions do not prevent unrelated rules from running.
6. Disabled rules emit no issues.
7. Engine and catalog contain no direct ATLAS state, selector, navigation, persistence, API, database, export, or rendering dependency.
8. Tests cover successful evaluation, malformed catalog, duplicate issues, aggregation, disabled rules, and evaluator failure.
9. Current ATLAS validation and UI behavior remains unchanged.
10. Documentation and project tree include only files actually created.
