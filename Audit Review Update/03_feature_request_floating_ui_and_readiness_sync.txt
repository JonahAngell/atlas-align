## 5. Desired Behavior
Required behavior:
- One shared host contains a floating circular control and issue panel.
- Hide or disable the control when no audit is active according to existing navigation-lock behavior.
- Green/checkmark for no warning or critical issue; yellow/warning icon for warnings without critical; red/alert icon for any critical issue.
- Expose severity and counts in accessible names/status text; color is not the only signal.
- Position in the lower-left content area without overlapping the fixed sidebar, dialogs, tutorials, primary controls, or narrow-screen navigation.
- Opening moves focus into the panel; Escape/close dismiss; closing restores focus.
- Panel displays summary counts, filters for all/critical/warning and category, grouped issue cards, empty state, and safe evaluation error state.
- Issue cards display severity, title/summary, detail, owning page, step/condition context where available, and disabled placeholders for future Jump/Fix actions as appropriate. Do not implement navigation or mutation in this phase.
- Readiness & Review renders the identical canonical issue result and includes summary counts and category status.
- Refresh invalidates/re-evaluates canonical results rather than calling a separate validator.
- If popup and Readiness are both visible, both update consistently after canonical invalidation.
- Evaluation/rendering should be coalesced and must not broadly recreate the selected Logic Builder editor.
Expected user flow: Active audit loads, floating state reflects issues, user opens panel or Readiness, filters/reviews issues, closes with restored focus.
Source of truth: Phase 2 canonical issue result.
Null/error behavior: No audit state; no issues; rule-load failure; evaluator failure; and stale target descriptions each have explicit accessible UI.
Preferred implementation: sections/audit-issues.html and css/audit-issues.css own shared UI; Readiness CSS owns page-only layout.
Required implementation: One host and one canonical result, no issue mutation/navigation yet.

## 6. Acceptance Criteria
1. One floating status control exists for an active audit and no duplicate host appears after repeated renders.
2. Status aggregation uses critical precedence and communicates state by icon, text, and color.
3. Selecting the control opens one accessible issue panel and closing restores focus.
4. Panel filters and category grouping do not recompute or mutate issues.
5. Panel and Readiness render identical issue IDs, severities, summaries, and totals for the same canonical result.
6. No-audit, no-issue, catalog/evaluator error, and empty-filter states are accessible and actionable.
7. UI works with keyboard, focus trapping, light/dark themes, forced colors, reduced motion, desktop, and narrow layouts.
8. Indicator/panel do not obstruct sidebar, tutorials, Visual Picker, Join Picker, or core actions.
9. Existing validation compatibility and all audit mutations/persistence remain unchanged.
10. CSS source, manifest if changed, and generated styles.css are consistent.
