+# Recommended Copilot Agent Instructions for Update Requests
+
+Add the following section to the agent instructions. It is designed to standardize request intake without forcing unnecessary questions or blocking straightforward work.
+
+## Update Request Intake and Formatting
+
+When helping the user prepare a code update request, format the request using the headings in `FEATURE_REQUEST_TEMPLATE.md`.
+
+For a complex, cross-file, business-rule, database, import/export, or architectural update, use the complete template. For a narrow and low-risk update, use the condensed template.
+
+Preserve all facts supplied by the user. Do not invent requirements, affected files, selectors, functions, business rules, acceptance criteria, or test results. Clearly label any recommendation as a recommendation rather than an established requirement.
+
+A well-formed update request should identify, when applicable:
+
+- Request type and title
+- Goal and business context
+- Current behavior and problem
+- Desired behavior and expected user flow
+- Objective acceptance criteria
+- In-scope and out-of-scope work
+- Likely affected files and protected files
+- Related functions, selectors, routes, tables, or components
+- Data inputs, outputs, source-of-truth fields, and edge-case handling
+- UI states, responsive behavior, overflow behavior, and accessibility expectations
+- Technical constraints and regression protections
+- Validation commands and test scenarios
+- Authoritative attached files and reference materials
+- Preferred deliverable format
+
+If information is missing, classify it as either blocking or non-blocking.
+
+- Ask concise follow-up questions only for blocking gaps that prevent a safe or accurate implementation.
+- Do not repeat a question the user has already answered.
+- Do not ask the user to reconfirm facts already present in uploaded files or project documentation.
+- For non-blocking gaps, proceed using the smallest reasonable assumption, disclose the assumption, and avoid expanding scope.
+- If the user specifically requests a best-effort implementation without questions, proceed with documented assumptions unless doing so would risk data loss, a security issue, an irreversible migration, or a materially incorrect business rule.
+
+Before implementation, restate the accepted scope in a short Implementation Contract containing:
+
+1. Goal
+2. Files expected to change
+3. Behaviors that must remain unchanged
+4. Acceptance criteria
+5. Deliverable format
+6. Blocking assumptions, if any
+
+Use the most recently attached files as the authoritative implementation source. Do not substitute archived, prior-conversation, generated, SharePoint, or repository-history versions unless the user explicitly directs you to use them. Project documentation and SharePoint sources may explain architecture and conventions, but they must not silently replace the current attached source files.
+
+For CSS changes in ATLAS Align:
+
+- Treat split files under `css/` as editable source.
+- Do not make source changes directly in generated root `styles.css`.
+- Identify the appropriate split CSS file and relevant source-unit placement.
+- Run or validate the CSS build workflow documented in `PROJECT_CONTEXT.md`.
+- Include generated `styles.css` and `css/manifest.json` in the deliverable only when they changed.
+
+For code delivery:
+
+- If the user already selected ZIP or patch delivery, use that format without asking again.
+- If no format was selected and both formats are feasible, ask one concise delivery-format question before implementation only when the choice materially changes the work.
+- Prefer full replacement files in a ZIP when patch application could fail because of version drift.
+- Include only files modified for the current request, plus required generated artifacts.
+- Never include unrelated, historical, or unchanged files merely to make the package appear complete.
+
+Before delivery:
+
+- Validate syntax.
+- Review imports and dependencies.
+- Validate file paths, references, and load order.
+- Check for obvious runtime and regression risks.
+- Run available, relevant tests and build checks.
+- Never claim a test was run if it was not run.
+- Identify assumptions, limitations, and any validation that could not be completed.
+
+Present the delivery response in this order:
+
+1. What changed
+2. Why it changed
+3. Modified files
+4. Validation performed and results
+5. Assumptions or limitations
+6. Downloadable deliverable
+7. Application and verification steps

+### Modular CSS
+
+#### CSS architecture and cascade contract
+
+The split files under `css/` are the editable CSS sources. The root `styles.css` file is generated output and should not be edited directly. Individual top-level CSS rules and at-rules are tracked as ordered source units using paired comments such as `ATLAS-SOURCE-UNIT:u0001:BEGIN` and `ATLAS-SOURCE-UNIT:u0001:END`. The unit's physical file indicates feature ownership, while its position in `css/manifest.json` controls final cascade order. Units from different files may therefore be interleaved in generated `styles.css`.
+
+Because later emitted rules can override earlier rules, moving a rule between files does not by itself determine precedence. Preserve or deliberately update its manifest position when changing ownership. New unmarked top-level rules are discovered by the build script and must have an unambiguous insertion location. Place them next to an existing marked unit, add an `ATLAS-INSERT-AFTER:u####` or `ATLAS-INSERT-BEFORE:u####` directive, use `ATLAS-INSERT:END`, or configure a default insertion location in the manifest.

+**Purpose:** Generated browser stylesheet assembled from the ordered units in `css/manifest.json`. It is the deployable compatibility artifact consumed by the application and must be regenerated after changes to split CSS files.

+**Editing rule:** Do not make source changes directly in `styles.css`; those changes can be overwritten by the next build. Edit the appropriate `css/*.css` file and rebuild instead.
+
+#### How to build the CSS
+
+**Prerequisites:**
+- Run the command from the project root, where `build-css.mjs`, `styles.css`, and the `css/` directory are siblings.
+- Use a Node.js environment that supports ECMAScript modules and the `node:` built-in import specifiers used by the script.
+
+**Recommended workflow:**
+
+1. Edit the appropriate split stylesheet under `css/`.
+2. Preview validation and discovery without writing files:
+
+```bash
+node build-css.mjs --check
+```
+
+3. Review any reported missing units, newly discovered units, insertion placements, or structural errors.
+4. Build and write the generated output:
+
+```bash
+node build-css.mjs
+```
+
+5. Review changes to the edited split CSS file, `css/manifest.json`, and root `styles.css` before committing them together.
+6. Run a strict verification that no unmarked CSS remains:
+
+```bash
+node build-css.mjs --check --no-discover
+```
+
+**Deletion workflow:** If a marked CSS unit was intentionally removed from its split source file, first preview the confirmed deletion without writing:
+
+```bash
+node build-css.mjs --check --accept-deletions
+```
+
+Then apply the deletion to the manifest and generated stylesheet:
+
+```bash
+node build-css.mjs --accept-deletions
+```
+
+Do not use `--accept-deletions` merely to bypass an unexpected missing-unit error. Restore the missing marked unit or investigate the manifest mismatch unless deletion was intentional.
+
+**Expected success output:** A normal build reports that `styles.css` was built from the ordered source units. Check mode reports that the CSS check passed and states how many units would be emitted. If new unmarked rules were found, the script reports the assigned IDs and their placements.
+
+**Build safety behavior:** The script rejects unknown options, unsafe paths, missing source files, invalid or duplicate unit IDs, mismatched or orphaned markers, ambiguous insertion locations, unbalanced CSS syntax, duplicate output emission, and generated output that still contains source-management markers. Writes use temporary files followed by rename operations.
